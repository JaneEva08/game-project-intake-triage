# Подробный сценарий видеозаписи VPk04.1

По заданию подготовь два отдельных ролика:

1. Демонстрация приложения — 2–3 минуты.
2. Защита проекта — 5–7 минут.

Скриншоты уже встроены в report.md. Они дополняют отчёт, но не заменяют видео, если куратор отдельно не разрешил такую замену.

## 1. Подготовься к записи

### Проверь сервер и Swagger

Сервер сейчас уже запущен. В открытом браузере должна быть страница:

    http://127.0.0.1:8000/docs

Если Swagger загружается, а в списке методов виден POST /triage, сервер готов. Не запускай второй экземпляр на этом же порту.

Если сервер остановился:

1. Открой папку проекта в Проводнике:
   G:\AI-Workspace\personal-workspace\outputs\VPk04.1-game-project-intake-triage
2. Нажми на адресную строку Проводника, введи powershell и нажми Enter.
3. Если виртуального окружения в этой папке ещё нет, выполни:

       python -m venv .venv
       .\.venv\Scripts\Activate.ps1
       pip install -r requirements.txt

4. Создай локальный .env из шаблона, если файла ещё нет:

       Copy-Item .env.example .env

5. Внеси в локальный .env свой API-ключ и пароль сотрудника. Не показывай этот файл на записи и не отправляй его в репозиторий.
6. Запусти приложение:

       uvicorn app.main:app --host 127.0.0.1 --port 8000

7. Открой Swagger: http://127.0.0.1:8000/docs

Если порт 8000 занят, останови только свой экземпляр uvicorn сочетанием Ctrl+C. Для другого порта измени PUBLIC_BASE_URL в локальном .env на тот же порт и запусти сервер на нём.

### Подготовь рабочий стол

1. Закрой лишние вкладки, личную почту, мессенджеры и уведомления.
2. Оставь Swagger и открой новую пустую вкладку для формы. Панель сотрудника откроешь позже.
3. Увеличь масштаб браузера до 110–125%, чтобы текст ответа читался в видео.
4. Проверь, что в кадре не видны .env, API-ключ, пароль, реальные переписки и личные данные.
5. Используй только вымышленные данные с доменами .example и example.test.
6. Если используешь запись экрана Windows, нажми Win+Alt+R. Останови и проверь тестовую запись заранее, чтобы убедиться, что браузер и звук записываются.

### Тестовый текст

Для каждого нового запуска используй новый client_id, например video-demo-20261109. Если этот запрос уже отправлялся сегодня, добавь окончание -2. Так результат не упрётся в лимит повторных запросов.

В Swagger используй такой JSON:

    {
      "text": "你好，我们是虚构的青竹工作室（Pine Lantern Studio）。我们希望为游戏《雾海纪事 / Tales of the Mist Sea》（https://games.example.test/mist-sea）寻求俄语本地化合作。请问贵团队是否有兴趣？我之后可以补充其他资料。",
      "channel": "email",
      "client_id": "video-demo-20261109"
    }

## 2. Видео 1: демонстрация, 2–3 минуты

### 0:00–0:15 — короткое вступление

Начни запись на странице Swagger. Скажи:

> «Покажу учебный сервис первичной обработки предложений от игровых студий. Он переводит входящее сообщение, сохраняет заявку и запрашивает недостающие сведения через форму».

### 0:15–0:55 — отправь предложение в API

1. Найди в списке и раскрой POST /triage.
2. Нажми Try it out.
3. Нажми в редакторе JSON, выдели всё сочетанием Ctrl+A и вставь тестовый JSON выше.
4. Проверь, что channel равен email, а client_id новый.
5. Нажми Execute.
6. Подожди, пока запрос завершится. Модель может отвечать несколько секунд.
7. Покажи ответ с кодом 201 и коротко прокомментируй:
   - category — other: это категория учебного API для нового предложения;
   - business_type — incoming_offer: бизнес-смысл обращения;
   - text_ru — перевод сообщения на русский;
   - missing_fields — какие сведения ещё нужны;
   - form_url — ссылка на форму разработчика.
8. Скажи: «Название студии и игры оставлены в оригинальном написании. Не хватает контакта и ссылки на материалы».

Не прокручивай весь длинный JSON. Расположи ответ так, чтобы были видны код 201, перевод, missing_fields и form_url.

#### Если вместо перевода показан fallback

Признаки fallback: text_ru равен null, уверенность низкая, эскалация включена, а черновик ответа остался на китайском языке.

В таком случае не говори, что LLM-перевод сработал. Останови эту попытку записи. Проверь, что API-посредник доступен, а локальный .env содержит правильные OPENAI_BASE_URL и OPENAI_MODEL. Для повторной попытки используй новый client_id. Ключ API в кадр не выводи.

### 0:55–1:35 — заполни форму разработчика

1. В ответе API выдели и скопируй значение form_url.
2. Переключись на новую вкладку.
3. Введи form_url в адресную строку и нажми Enter.
4. Покажи, что система уже подставила студию, название игры и страницу игры.
5. В поле Contact email введи:

       demo@pine-lantern.example

6. В поле Screenshots and video вставь:

       https://materials.example.test/mist-sea

7. В поле Additional note можно написать:

       Вымышленные данные для демонстрации

8. Нажми Submit · 提交.
9. Дождись сообщения об успешном сохранении и покажи его в кадре.

Скажи: «Разработчик дополнил ту же заявку. Контакт и ссылка на материалы теперь сохранены вместе с остальными данными игры».

### 1:35–2:20 — проверь карточку сотрудника

1. Открой новую вкладку и перейди по адресу:

       http://127.0.0.1:8000/admin

2. Если появится запрос авторизации, введи локальные ADMIN_USER и ADMIN_PASSWORD. Начни запись после ввода или останови её на время авторизации. Не показывай пароль.
3. В списке заявок открой самую свежую запись — ту, которую только что отправила.
4. Покажи:
   - оригинальное сообщение на китайском;
   - перевод на русский;
   - данные студии и игры;
   - email и ссылку на материалы;
   - статус awaiting_staff_review.
5. Не меняй данные во время демонстрации, чтобы случайно не изменить тестовую заявку.

Заверши:

> «После дополнения заявка остаётся на проверке сотрудника. Сервис не принимает решение о сотрудничестве автоматически».

### 2:20–2:50 — если нужно уложиться в лимит

Оставь вступление, успешный ответ API, заполнение формы и карточку сотрудника. Сократи ожидание ответа и переходы между вкладками. Итоговый ролик должен быть 2–3 минуты.

## 3. Видео 2: защита проекта, 5–7 минут

Защиту записывай отдельно. Можно говорить поверх демонстрации интерфейса и коротко показывать README.md, report.md и исходный код. Не открывай .env.

### 0:00–0:50 — проблема и пользователь

Скажи:

> «Проект предназначен для команды, которая рассматривает игровые проекты на локализацию. Предложения могут приходить на разных языках и без обязательных сведений — например, контакта или ссылки на материалы. Сервис приводит входящее сообщение к единому виду и помогает запросить недостающее».

Покажи Swagger или первую часть отчёта.

### 0:50–1:35 — границы MVP

Объясни:

- приложение обрабатывает входящее предложение об игре;
- входящие сообщения почты и чатов не подключены автоматически;
- реальная отправка ответа не выполняется: сервис готовит текст, который сотрудник отправляет сам;
- перевод и сведения проверяет человек;
- решение о сотрудничестве, инвестициях или публикации приложение не принимает;
- финансовая проверка и оценка инвесторов/маркетинга относятся к дальнейшему этапу общей темы.

### 1:35–2:20 — API и входные данные

Покажи POST /triage или раздел отчёта «Входные данные».

Объясни три обязательных поля:

- text — исходный текст обращения;
- channel — метка источника email, form или chat;
- client_id — идентификатор отправителя или тестового источника.

Скажи, что FastAPI проверяет структуру запроса, а SQLite сохраняет обращения и этапы обработки.

### 2:20–3:10 — архитектура

Покажи README, report.md или исходные файлы app/main.py и app/llm.py.

Расскажи цепочку:

1. POST /triage принимает и валидирует сообщение.
2. Модель классифицирует предложение, выделяет доступные сведения и переводит сообщение.
3. Приложение проверяет ответ по структуре и сохраняет запись в SQLite.
4. Если данных не хватает, создаёт персональную ссылку на форму.
5. После заполнения формы информация связывается с исходной заявкой.
6. Сотрудник проверяет и дополняет карточку.

### 3:10–4:50 — короткая демонстрация

Покажи уже подготовленный сценарий:

1. Swagger: успешный ответ 201 с переводом и списком missing_fields.
2. Форма разработчика: предзаполненные данные плюс добавленные контакт и материалы.
3. Панель сотрудника: оригинал, перевод, дополненные данные, статус проверки.

Не отправляй много повторных запросов: для демонстрации достаточно одной тестовой заявки.

### 4:50–5:40 — ошибки и надёжность

Расскажи по факту:

- если LLM не отвечает или возвращает некорректный результат, приложение использует fallback и помечает обращение для ручной проверки;
- форма связана с исходной заявкой и не создаёт отдельную игру без связи с обращением;
- есть ограничение частоты запросов по client_id;
- есть журнал заявок и событий в SQLite.

Не утверждай, что письма отправляются автоматически или что данные проверяются на достоверность.

### 5:40–6:20 — безопасность и человеческая проверка

Скажи:

> «В демонстрации используются только вымышленные данные. API-ключ хранится в локальном .env и не публикуется. LLM готовит перевод и черновик, а сотрудник проверяет полноту и корректность сведений. При публичном размещении панели нужны HTTPS и защищённая конфигурация».

Не открывай файл .env на экране.

### 6:20–6:50 — развитие проекта

Расскажи:

> «Следующий этап общей системы может собирать финансовые показатели LTV, ARPPU, retention и conversion, запрашивать условия по территориям и формировать документ для оценки staff, инвесторами и маркетингом. Это развитие следующего этапа, а не готовая функция текущего MVP».

Заверши кратко:

> «В текущем MVP проверен путь от входящего предложения до дополненной заявки, переданной сотруднику на review».

## 4. Перед сохранением и отправкой

Проверь оба ролика:

- демонстрация длится 2–3 минуты, защита — 5–7 минут;
- в начале каждого ролика понятно, какую задачу решает проект;
- видны реальные действия и ответы интерфейса;
- в демонстрации API вернул 201, text_ru содержит перевод, а missing_fields показывает только недостающие данные;
- форма подтвердила отправку, сотрудническая карточка показывает ту же заявку;
- в кадре нет API-ключей, паролей, .env, личных переписок и реальных данных;
- ты не называешь отправку писем, Due Diligence или принятие решений реализованными функциями.

Сохрани файлы, например, как VPk04.1-demo.mp4 и VPk04.1-defense.mp4. Передавай их куратору способом, указанным в учебной платформе. Не добавляй видео в публичный репозиторий, если куратор этого не просил.
